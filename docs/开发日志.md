# Compositor 简体中文语言包（v1.6.4 · v3 语言包驱动版）

## 一、结论先说

**这个软件没有语言设置，官方也不打算有。** 仓库 README 的 `Translations` 一节原文：

> "Compositor is English only for now, and translation pull requests aren't being accepted.
> It's maintained by one person, every new string would need translating from then on,
> and translations in languages I don't read can't be reviewed."

即：作者一人维护，后续新增文案无法持续翻译，也审不了自己不懂的语言，因此**暂不接受本地化 PR**。

> **✅ 2026-11-08 v3 更新：本项目已完成源码全量改造，当前正式包为「语言包驱动」架构** ——
> 更换/修改任何界面文案，只需替换 App 包内 `Localizable.strings`，**无需改源码重编译**（详见第十节）。

本地 App 包里也确实没有任何本地化资源：`CFBundleDevelopmentRegion = en`，无 `CFBundleLocalizations`，
`Contents/Resources` 下只有图标、Assets.car 和两张 Camera Raw 查找表；唯一的多语言目录来自第三方升级框架 Sparkle。

## 二、汉化是怎么做到的

软件是 SwiftUI 写的（源码 295 个 Swift 文件，MIT 许可，`github.com/robbietilton/Compositor`），
界面文案全部是 `Text("...") / Button("...") / Label("...")` 这类**字符串字面量**，
源码里 `Text(verbatim:)` 和 `NSLocalizedString` 都是 0 处 —— 也就是说 SwiftUI 会隐式把它们当作
`LocalizedStringKey`，运行时去 main bundle 查 `Localizable.strings`。

所以**基础汉化不需要改二进制、不需要重新编译**（下拉控件等四类例外见第四节，已由第九节的重编译补齐）：

1. 往 App 包里放 `zh-Hans.lproj/Localizable.strings` 与 `en.lproj/Localizable.strings`（同一份中文表）；
2. 把 `Info.plist` 的 `CFBundleDevelopmentRegion` 由 `en` 改为 `zh-Hans`，并声明 `CFBundleLocalizations`；
3. 因修改了包内容，**只对主程序做 ad-hoc 本地签名**（保留原沙盒授权，
   并追加 `com.apple.security.cs.disable-library-validation`）；
   `Sparkle.framework` 及其内部 XPC/Updater 一律保持官方签名，不做重签。

系统语言本来就是简体中文，无需改任何偏好设置。实测 11 条真实词条全部命中中文。

> 注：实测发现 Bundle 的 `preferredLocalizations` 仍返回 `en`（即便系统语言是简体中文），
> 只放 `zh-Hans.lproj` 而**不**改 `CFBundleDevelopmentRegion` 时完全不查中文表。
> 因此在 `zh-Hans.lproj` 与 `en.lproj` 各放一份，同时把开发区域改为 `zh-Hans`，
> 覆盖「按首选语言查」与「按开发区域回退」两条路径。

## 三、翻译口径

- 术语对齐 **Adobe Photoshop 中文版**（如 Multiply→正片叠底、Linear Dodge (Add)→线性减淡（添加）、
  Color Range→色彩范围、Content-Aware Fill→内容识别填充、Feather→羽化、Proof Colors→校样颜色）。
- 按功能语义译，不做字面直译：如 `Highlight Recovery` 译"高光恢复"、`Dehaze` 译"去除薄雾"、
  `Upright` 译"垂直校正"、`Bake and Delete` 译"固化并删除"。
- 保留不译：产品名 Compositor、相机／设备名（Studio Display、iPhone 18 Pro）、
  算法与格式专名（Floyd–Steinberg、Bayer、Atkinson、Helvetica、sRGB、CMYK、RGB、Alpha、HDR）、
  快捷键符号与按键名（⌘、Option、Return）。
- 菜单末尾的 `…`、单位、数字格式一律保留。
- 完整对照见 `术语表.md`；`zh-Hans.lproj/Localizable.strings` 共 **1645 条**（`plutil` 解析后的真实 key 数，含插值占位符变体与状态栏动态拼接串），按模块加了注释。

## 四、⚠️ 覆盖范围的硬限制（历史原理说明，v3 已解决）

语言包只作用于 SwiftUI 的 `LocalizedStringKey` 路径（`Text("…")` / `Button("…")` / `Label("…")` 字面量）。
v3 之前，源码里有四类文案**绕开了本地化表**，往 `.strings` 里补多少词条都不会变中文：

| 类型 | 源码写法 | 实际界面上的英文 |
|---|---|---|
| 参数声明为 `String` | `dimension(_ title: String, …)` → `Text(title)`、`help: String` | `Width`、`Height`、`Pixels` |
| 枚举 `rawValue` 直接当显示文本 | `ForEach(ShapeKind.allCases) { Text($0.rawValue) }` | `Rectangle`、`Ellipse`、`New`、`Add`、`Subtract` |
| 字符串插值 / 计算属性 | `"\(rawValue.capitalized) canvas"`、`"\(Int(resolution)) DPI"`、`?? "Untitled"` | `Transparent canvas`、`72 DPI`、`Untitled` |
| **AppKit 控件标题** | `NSPopUpButton.addItem(withTitle: mode.rawValue)` | **混合模式下拉 24 项**、字体选择下拉 |

其中混合模式下拉（`UI/BlendModePicker.swift`）尤其特殊：它不是 SwiftUI `Picker`，而是
`NSViewRepresentable` 里包了一个 AppKit `NSPopUpButton`，菜单项标题直接取 `LayerBlendMode.rawValue`。
`Localizable.strings` 对 AppKit 菜单标题**完全无效**。而且 `rawValue` 还同时用于
`LayerBlendMode(rawValue: $0.title)` 反查选中项、以及文档持久化 —— 所以也不能只把菜单标题改成中文，
那会让反查失败、混合模式选不上。

**结论：只装语言包时，要翻译这批文本必须改可执行程序（源码重编译或二进制修改），语言包做不到。**

✅ **v3 已通过源码全量改造彻底解决这四类**（见第十节）：所有变量显示点统一包 `L()` 查表入口，
AppKit 菜单标题全部查表、选中反查改用 `representedObject`/`rawValue` 与显示语言解耦。
**当前正式包是纯语言包驱动**：界面文案 100% 由 `Localizable.strings` 决定，改文案/换语言不用再碰源码。
下表保留作为历史记录与原理说明。

## 八、启动崩溃事故与修复（2026-11-08）

现象：打开即报「Compositor 意外退出」，崩溃日志关键行：

> `Termination Reason: Namespace DYLD, Code 1, Library missing`
> `Library not loaded: @rpath/Sparkle.framework/Versions/B/Sparkle`
> `... mapping process and mapped file (non-platform) have different Team IDs`

根因：改包后主程序是 ad-hoc 签名（`TeamIdentifier=not set`）且带 hardened runtime，
library validation 要求被加载的 framework 与主程序有相同 Team ID；
旧脚本把 Sparkle 及内部 XPC/Updater 也一并 ad-hoc 重签，两个「空 Team ID」无法互认，
dyld 在启动阶段直接 abort。**与中文资源无关，纯签名问题。**

修法（先在 `/tmp` 副本上实测两种方案，选破坏面最小的）：

1. 从原版备份还原 `Sparkle.framework`，保留官方
   `Developer ID Application: Wonder Assembly LLC (3E4X3B9Z9T)` 签名；
2. 只重签主 bundle，授权追加 `com.apple.security.cs.disable-library-validation = true`；
3. 脚本第 ⑤ 步加自检：缺该授权直接报错退出，避免再装出「验签通过但启动即崩」的包。

验收：脚本连续重跑两次 `EXIT=0`；进程正常存活；无新增崩溃报告；中文词条 11/11 命中；
`codesign --verify` 有效；`Info.plist` 30 字段完整；Sparkle 恢复官方签名。

脚本开发中另外修掉三处会让 `set -e` 静默中断的坑：
`plutil -replace ... -json` 会覆盖整个 plist（改用 Python `plistlib`）；
`codesign -d --entitlements -` 少了冒号（正确写法 `:-`，否则导出空数据）；
`mktemp /tmp/xxx.XXXXXX.plist` 在 macOS 上把模板当字面文件，第二次运行报 `File exists`（改成以 `XXXXXX` 结尾）。

1. **`import Sparkle` 编不过**：App 内置 `Sparkle.framework` 2.10.0/2064 是精简版，
   只有运行时文件，没有 `Headers` / `Modules/module.modulemap`。官方 SDK（16 MB）下载超时，
   改为从 jsDelivr / raw 拉取 22 个公开头文件、递归补齐依赖，自造 umbrella + modulemap，
   动态库仍用 App 内官方二进制。`import` 探针 `EXIT=0`。
2. **SwiftUI `@State` 宏插件缺失**：SDK 27.2 把 `@State` 实现成宏，编译需要 `SwiftUIMacros`；
   CommandLineTools 只带 `SwiftMacros` / `ObservationMacros` / `TestingMacros`（完整 Xcode 才有）。
   改用本机的 **`MacOSX26.5.sdk`**（target `arm64-apple-macos26.5`，在 macOS 27.2 上向后兼容），
   宏依赖消失。
3. **一批 `@MainActor` 隔离 hard error**：工程 `project.pbxproj` 明确设了
   `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`，裸 `swiftc` 不知道。

### 12.2 导出插件（导出插件/ 目录）

`WebExportPlugin.swift` —— C ABI v2，schema 声明 `interaction: "export"`：

| 格式 | 编码管线 | 压缩维度 | 透明处理 |
|---|---|---|---|
| WebP 有损 | **vendored libwebp 1.6.0**（高级 API，method 随档位 4/5/6） | quality 1–100 | alpha 保留（反预乘） |
| WebP 无损 | libwebp lossless（effort 75 官方推荐） | — | alpha 保留 |
| JPEG | ImageIO | quality 1–100 | 白底填充 |
| PNG 全彩 | ImageIO（无损 RGBA） | — | alpha 保留 |
| PNG8 调色板 | 中位切分量化（2–256 色）+ **手写 PNG chunk**（PLTE + tRNS 二值透明 + zlib deflate 等级 9 + CRC32） | 颜色数、Floyd–Steinberg 抖动 | 全透明像素 → palette[0]（阈值 0） |
| GIF | 同一量化管线 + **手写 GIF89a**（LZW 压缩 + Graphic Control Extension 透明 index） | 颜色数、抖动 | 透明 index 0 |

- **缩放**（5–100%）是体积压缩的第一杠杆（CGContext 高质量重采样）。
- 档位：高质量（q92/全彩）/ 标准（q82/全彩，默认）/ 极限（q62/PNG8 64 色）/ 自定。
- 元数据最小化：渲染像素本无 EXIF/GPS，仅显式写 DPI 72。
- libwebp 为 vendored 源码（`libwebp-src/`，1.6.0，109 个 C 目标编 arm64 静态库 564K 随插件链接）。
  ⚠️ macOS 27.2 的 ImageIO **不支持 WebP 编码**（探针实证：4 种 UTI 全部不可创建 destination，
  解码倒是支持）——所以 WebP 必须自带编码器。
  ⚠️ libwebp 的 `WebPConfigInit` 等是 `static WEBP_INLINE`，Swift 看不见 → `webp_shim.c`
  提供 C 包装（shim_WebPConfigInit 等）。
- `编译导出插件.command`：libwebp 静态库 → shim → swiftc 插件（链接 -lz）→ bundle → 装入
  `Contents/Plugins/` → 重签主 bundle → 验签。

## 十四、v4.2 修复：Web 导出预览永久「正在更新…」（2026-11-09 凌晨）

老朱真机报：Web 导出面板预览转圈很久不出图，「正在更新…」不消失、导出按钮灰。

### 14.1 排查过程（诊断副本 + 进程采样）

- `sample` 采样卡住进程 3 秒：**主线程空闲（等事件）、全部工作线程睡觉——零编码活动**；
  无崩溃报告；峰值内存 236M > 常驻 132M（曾有大块分配又释放）。
- 预览走 `.task(id: settingsHash)`，settingsHash 取 `paramsJSON`（JSONSerialization）输出。
  给源码加探针 + **非沙盒副本直接 exec 拿 stdout** 实测复现（1600×1000 文档自动触发 Web 导出）。
- ⚠️ 诊断过程踩坑三连（记录防复发）：① 沙盒 App 写 /tmp 被拒且 `try?` 静默吞错；② 工具侧读
  容器被 TCC 挡、`log show` 在沙盒内禁跑、`open --stdout` 对沙盒 App 无效；③ **非沙盒副本
  （entitlements 只留 disable-library-validation）直接 exec 可自由输出 stdout**——最有效的复现
  通道。另外：**手动换二进制必须带完整 entitlements 重签**，漏了会丢沙盒授权 → Sparkle
  library validation → 启动即崩，且 LaunchServices 静默吞掉不报错。

### 14.2 根因（实锤）

**新版 Foundation 对 JSONSerialization 的字典键序做了轮换随机化**（防哈希碰撞）：
同内容的参数字典，跨时间两次 `JSONSerialization.data` 输出**键序不同**（同进程实测复现，
内容逐字节相同、仅键排列变化）。

于是 `.task(id: settingsHash)` 的 id **每次 body 求值都在「变」**：
1. task 频繁被取消重启，300ms debounce 后 guard 的 `requested == settingsHash` 常态失败 → 静默 return；
2. 偶尔键序恰好一致 → 编码成功 → await 返回后 hash 又变 → **结果被当「过期」丢弃**；
3. 即使 `result` 赋值成功，下一次 body 求值 hash 又变 → `isReady=false` → 永远「正在更新…」。

v4.1 冒烟测试直接调 `encodeImage`（不经 `.task(id:)`），GUI 验证受辅助功能限制未做——雷留到现在。
